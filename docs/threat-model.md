# Threat model

This document says what the safeguards of agentic-sdlc-kit are meant to stop, what each one really guarantees, and what an agent that wants to get around them can still do. It is for owners who decide how far to trust a setup, and for contributors who change the rules. Read it together with INSTALL.md ("Harness hooks and trust", "Owner, agents and tokens", "Secret guard").

In one sentence: **the kit is a set of guardrails and an audit trail for agents that mostly follow their instructions. It is not a sandbox.** An agent that can run shell commands as you can undo most of what the hooks do. What holds against it is review of the pull request, branch protection that binds the agent's account, and a separate agent account. The hooks are what makes the honest path easy and the shortcuts visible.

## Scope

The kit defends against:

- an agent that cuts a corner by mistake: editing code before the plan is approved, committing to the default branch, skipping a hook, merging with admin rights, starting another AI tool, committing a secret;
- an agent that is steered into one of those by text it reads (an issue, a web page, a file), through the obvious route;
- loss of the state of a task when GitHub or the network is down.

It does not defend against:

- a determined attacker, or an agent acting like one, with code execution on the machine and the owner's credentials;
- a stolen or over-privileged GitHub token, or a compromised GitHub account;
- vulnerabilities in the harnesses (Claude Code, Codex, Gemini CLI), or in `git`, `gh` and Node;
- a compromised dependency of the kit itself.

## Assets

1. **The default branch**, and whatever is released or deployed from it.
2. **Secrets**: tokens, keys and the contents of `.env` files, in the working tree, in git history and on the remote.
3. **The owner's decisions**: approvals, acceptances, cancellations, confirmations that a production-data script was run, merges. The point of the kit is that these are given by the owner, and that the record says so.
4. **The task record**: the issue, its hidden state comment, the board, the evidence and the gaps.
5. **The rules themselves**: `sdlc.config.yaml`, `.sdlc/` (the git hooks, the hook launcher, the manifest), the harness settings files, the instruction files and the agent roles.
6. **The owner's credentials**: the `gh` login, `GITHUB_PERSONAL_ACCESS_TOKEN`, the `SDLC_TOKEN` secret and the OS keystore. The kit never writes them into the repository, but every command an agent runs in a shell has whatever the shell has.
7. **Production systems and data** that a task may touch.

## Actors

- **The owner.** Decides, and is trusted. Their GitHub login is listed under `owners`.
- **An agent under the owner's login.** The agent runs `gh` as the owner. Everything the owner's token can do, the agent's shell can do. The tool cannot tell a comment written by the owner from one written by the agent, so in `enforce` mode comment approvals are refused and the owner approves by typing the command in a prompt (see "Approvals").
- **An agent under its own login**, listed under `agents`. This is the recommended setup. Its comments never count as owner approvals, and its token can be given fewer rights (no admin rights, no right to merge into the default branch if the plan allows), so that branch protection binds it.
- **Other contributors.** People with write access who use plain git, and people who open pull requests from forks. The harness hooks do not run for them, and the git hooks run only in a clone that has set `core.hooksPath`. Branch protection and review are what bind them. Only state comments written by a login under `owners` or `agents` are read as task state. The reconcile workflow skips Dependabot runs and installs the kit in a step that has no token.

An agent that is manipulated by hostile text is treated as an agent under whichever login it runs as.

## Layers and what each guarantees

| Layer | What it is | What it guarantees | What it does not guarantee |
|---|---|---|---|
| Instructions | the managed block in `CLAUDE.md` / `AGENTS.md` / `GEMINI.md`, the skills and the agent roles | nothing by itself: they tell the agent the rules | that the agent reads, remembers or follows them |
| Harness hooks | `sdlc hook` run by Claude Code, Codex and Gemini CLI at session start, on each prompt and before each tool call | while they run and the call goes through the paths they read: in `enforce` a matching call is refused before it runs; in `observe` it is allowed, with a warning; either way a gap is recorded on the task | that they run at all; that a call is seen; that shell commands and shell edits are read through |
| Git hooks | `.sdlc/githooks`: `pre-commit`, `pre-push`, `post-merge`, `post-checkout` | in a clone that has set `core.hooksPath` and can resolve `sdlc`: the secret guard on commit and push, and in `enforce` the branch rules | anything when `--no-verify`, a changed hooks path or a missing `sdlc` is in play |
| Secret guard | the scan in `pre-commit` and `pre-push` (built-in patterns, and gitleaks if installed) | a known secret shape in a staged or pushed change is refused, in both modes; it fails closed, so a guard that cannot scan blocks; only a masked value and a fingerprint are printed | secrets in a shape no pattern knows, split or encoded secrets, a commit made with the hooks off, or a hook that cannot run because `sdlc` is not resolvable (the hook is skipped) |
| Branch protection | classic protection on the default branch, set by `init` when it has none | a pull request is required, and force pushes and deletions are refused, for accounts without admin rights | anything for an admin: the kit sets `enforce_admins: false` and no required reviews, so an account with admin rights can merge or push around it |
| Approvals | an owner's comment, or a command typed in a prompt | a recorded approval came from a comment by an owner login, or from a human prompt that the hook read | a distinction between the owner and an agent that holds the owner's token |

### Instructions

The block, the skills and the roles are read by the agent and nothing else enforces them. Their job is to make the agent do the right thing without being stopped. Instruction files are Markdown, and Markdown needs no task (see "Known bypasses"), so an agent can edit them. `sdlc upgrade` restores the managed block, `doctor` (`files.managed`) reports edited managed files, and the change shows in the pull request.

### Harness hooks

Three events, one program: `sdlc hook <harness> <event>` behind the launcher `.sdlc/hooks/run.sh`.

- **Session start** tells the agent which task its branch has and starts `sdlc sync` in the background if something is queued.
- **Prompt** reads the first non-empty line of a human prompt for an owner command and records it (see "Approvals"). Prompts of subagents are ignored where the harness marks them.
- **Pre-tool** checks the call:
  - file edits: no tracked task for the branch, a plan not yet approved, a finished task, or a protected path (`sdlc.config.yaml`, `.git`, `.sdlc/` except `.sdlc/agents/custom/`, and the harness settings: `.claude/settings.json`, `.claude/settings.local.json`, `.codex/hooks.json`, `.codex/config.toml` and `.gemini/settings.json` at any depth, `.mcp.json` at the root, and the same files plus `.claude.json` in the user's home directory; protected paths are refused in `enforce` only);
  - subagent dispatches without a role and a model tier (an `sdlc-<role>` agent counts, and Gemini payloads carry no model, so in `enforce` Gemini built-in agents are refused);
  - shell commands: `gh pr merge --admin`, merging through `gh api` (`api-merge`: the endpoint `.../pulls/<n>/merge` unless the method is explicitly GET or HEAD, or a GraphQL call that names `mergePullRequest` or `enablePullRequestAutoMerge`; refused in `enforce` only), another AI CLI (`claude`, `codex`, `gemini`, `aider`, `cursor`, `cursor-agent`, `ollama`, `opencode`, `goose`, `llm`, `sgpt`; `--version` and `mcp`, `plugin` or `extensions` `list` are allowed), `--no-verify`, turning the git hooks off through git config (`core.hooksPath`, `include.path`), force pushes, `git worktree prune` and forced `git worktree remove`, `rm -rf`, `sdlc config set`, `sdlc uninstall` and `sdlc init --overwrite-modified` (`kit-removal`), and running `sdlc hook` or the launcher by hand. The `sdlc` rules also read `node <dist>/cli.js ...` (`cli.js` directly in a `dist` directory, such as `node ./node_modules/agentic-sdlc-kit/dist/cli.js`; a deeper `dist/tools/cli.js` is not read) and `node_modules/.bin/sdlc`, run directly or through `node`.

  In `enforce` the first matching rule refuses the call with a message that names the rule. In `observe` the call goes ahead, with a warning. Either way each violation is recorded as a gap: the rule, the text, the harness and whether it was refused. The state comment keeps the 20 newest gaps. Running the hooks by hand (`hook-spoof`) and removing the install (`kit-removal`) are refused in both modes. A call that breaks several rules records each as refused, though only the first is named in the refusal.

Docs (`docs/**`) and any `*.md` file need no task. Edits are allowed in `debugging` and in task types that have no planning phase; otherwise the plan has to be approved. The state of the task is cached for 10 minutes in `.sdlc/cache/hook-tasks.json`, only when edits were allowed, so an approval takes effect on the next edit.

What the harness hooks guarantee is narrow: when the harness runs them, and the tool call reaches them in a form they read, a call that breaks a rule is refused (`enforce`) or recorded (`observe`). Everything else is in "Known bypasses". The kit leans on each harness treating a hook that fails or times out as non-blocking, and does not ask any harness to block on a hook failure.

### Git hooks and the secret guard

- `pre-commit`: the secret guard, then in `enforce` a refusal of commits to the default branch.
- `pre-push`: the secret guard on the pushed commits, then in `enforce` a refusal of pushes to the default branch and of `task/*` branches whose task is not tracked. It looks the task up on GitHub; when GitHub cannot be reached in time, it allows the push with a warning.
- `post-merge`: starts a reconcile in the background. `post-checkout`: prints the task of the branch.

The guard blocks in both modes and fails closed. The rest are branch rules and fail open: an unreadable config, an unknown hook or an unexpected error prints a warning and lets git go on. `core.hooksPath` is local git config, so it is set again in every clone (INSTALL.md, Step 4). `sdlc` has to resolve (on the PATH, or through `npx --no-install sdlc`); when it does not, the hook says the guard is not active and lets the commit through. GitHub secret scanning push protection is the server-side backstop where the plan has it.

### Branch protection and the merge policy

`init` sets classic protection on the default branch when it has none: a pull request is required, no approving reviews, no force pushes or deletions, administrators not included. Without required reviews, one account can open and merge its own pull request, so the merge policy (`owner_only` or `agent_on_request`) is a rule in the instructions. The mechanical parts are only that a pull request is required, and that the harness hooks refuse `gh pr merge --admin` and a merge through `gh api` (in `enforce`); any other route to the same merge (see "Known bypasses", item 7) is not refused. A repository that uses rulesets keeps its own rules, which `init` does not read. A free private repository, or a token without admin rights, cannot have protection at all.

### Approvals

- **By comment.** `sdlc approve ... --comment-url <url>` reads the comment from GitHub and checks that its author is an owner, and that it was not written by the login `sdlc` acts as (or by a login under `agents`). If the tool's login is the owner's own, an owner comment is indistinguishable from the agent's own, so `enforce` refuses it and `observe` records it as `unverified`.
- **By prompt.** When the first non-empty line of a human prompt is `/approve`, `/accept`, `/ran` or `/cancel <reason>`, the prompt hook records it on the task of the current branch. `/approve` covers the current phase; the others cover the task; `/approve type <id>` is comment-only. The record carries a reference built from the harness, the session, the prompt id and a hash of the prompt. The prompt text is never stored. With one owner it is recorded for that owner whichever login `gh` runs as; with several, the login `gh` runs as has to be one of them. The agent cannot type into its own prompt line, and the hook refuses an agent that tries to call it.
- **A comment on a pull request** counts for a task only when the PR's body links that task and no other, and the body was not edited after the comment. Without the second rule, an owner's `/approve` on a PR that linked task A could be made to approve task B by editing the body to say `Related to #B`. The edit time is GitHub's `lastEditedAt`, read with one GraphQL query for the PRs of a task; a comment older than the last edit is ignored (`ignored_approval` in `reconcile`, a refusal in `approve --comment-url`), and the owner repeats the command. The same command posted on the task issue is not affected. If that query fails, the edit time is unknown, a warning is printed and the comment counts as before (see item 30).
- `--unverified`, which records an approval without checking its author, exists only in `observe`. It is dated from the stamps of what it approves (GitHub's publish times, and the reopen time, which the local clock of whoever reopened the task wrote), never from the local clock alone: the approval is never placed before what it approves, whether the local clock runs ten minutes fast or slow, and with a clock that is ahead it keeps the local time.

## Known bypasses

These are stated plainly, because an owner should not discover them by surprise. None of them needs a vulnerability in anything: each is something the design does not look at.

### Shell commands the rule does not see through

The shell rule reads the text of the command. It follows wrappers (`env`, `sudo`, `exec`, `nohup`, `time`, `timeout`, `nice`, `stdbuf`, `xargs`, `npx`, `bunx`, `pnpm dlx`, `yarn dlx`, `npm exec`), follows `sh -c`, `bash -c` and `eval` down to three levels, and treats the body of a heredoc as data, so that a commit or pull request message that mentions a forbidden command is not refused. It never runs or expands anything. It therefore misses:

1. **Variables and substitutions.** `CLI=claude; $CLI -p x`, `$(which claude) -p x`, or any command whose name is built at run time.
2. **`find -exec`.** A program started by `find ... -exec` is not read.
3. **Nesting beyond three levels.** `sh -c "sh -c 'sh -c \"sh -c claude\"'"` is past the limit.
4. **Scripts written, then run.** The agent writes `x.sh` (with an edit tool or a redirect) and runs `sh x.sh`; the rule reads the second command only.
5. **Piped and fed heredocs.** Because heredoc bodies are data, `cat <<EOF | sh`, `bash <<EOF`, and a `$(...)` inside the body of an unquoted heredoc run commands the rule never reads.
6. **Aliases, functions and encoded text** decoded at run time.
7. **Another way to the same effect.** A rule names the spellings of what it forbids. `gh pr merge --admin` and a merge through `gh api` (`api-merge`: `gh api -X PUT repos/<owner>/<repo>/pulls/<n>/merge`, in any option order and with any method but an explicit GET or HEAD, and a GraphQL `mergePullRequest` or `enablePullRequestAutoMerge` mutation given in the command, names as written) are refused in `enforce`, and only warned about in `observe`. Other routes to the same merge are not: `gh pr merge --auto` (without `--admin`), which waits for the branch's required checks and so is governed by branch protection, not by the hook; a GraphQL query or a request body read from a file or stdin (`-f query=@file`, `--input`), an HTTP client with the token (`curl`), a GitHub MCP server's merge tool (9), a script that makes the call (4) or the web UI. An admin token merges with the same rights through any of them.

Every shell rule has this limit: `--admin` and `gh api` merges, other AI CLIs, `--no-verify`, turning the git hooks off through git config, force pushes, `git worktree prune` and forced `git worktree remove`, `rm -rf`, `sdlc config set` and the hook-spoof rule. Obfuscation is not an accident, so these rules stop the careless and the steered-by-accident, not the determined.

### Edits the edit rule does not see

8. **Shell-driven edits are not parsed.** The edit rule checks the harness's own edit tools: Claude Code's Edit, Write and NotebookEdit, Codex's `apply_patch`, Gemini CLI's `write_file` and `replace`. `sed -i`, `tee`, `>` and `>>` redirects, `cp`, `mv`, `git apply`, `patch` and scripts write files with no check. "No edits before the plan is approved" holds for edit tools, not for the shell. This includes the protected paths: a redirect into `sdlc.config.yaml` or into a file under `.sdlc/` is not refused.
9. **Tools the hooks do not see.** The pre-tool hook sees the calls the harness sends it. MCP tools that write files (a filesystem server, say) are not read by the edit rule. A shell command that a Claude Code skill injects into itself when it loads runs without a pre-tool call, so no shell rule sees it.
10. **Markdown and docs never need a task.** Anything under `docs/` and any `*.md` is exempt. That includes `CLAUDE.md`, `AGENTS.md`, `GEMINI.md`, the agent roles and the skills. A code change disguised as Markdown passes the harness hooks; the git hooks and review remain.
11. **The harness settings files are protected only from the edit tools, and only in `enforce`.** In `enforce` the edit rule refuses `.claude/settings.json`, `.claude/settings.local.json`, `.codex/hooks.json`, `.codex/config.toml` and `.gemini/settings.json` at any depth of the repository, `.mcp.json` at its root, and the same files plus `.claude.json` in the user's home directory. What stays open: the shell writes them with no check (8); in `observe` an edit tool changes them silently, with no warning and no gap, in the repository and in the home directory alike; and the trust state that decides whether a harness runs project hooks is outside the repository (13). Claude Code picks up edits to its settings while it runs. Codex asks for a new `/hooks` review when a hook changes, and Gemini CLI only warns once about a hook it has not seen. The change shows in the pull request, and `doctor` (`hooks.<harness>`, `hooks.switches`, `hooks.roundtrip`) notices hooks that are missing, switched off or that do not answer.
12. **Git configuration can still be changed from the shell, which turns the git hooks off.** The shell rule refuses `git config`, `git -c` and `git --config-env` that set or unset `core.hooksPath`, `include.path` or `includeIf.*.path` (as `no-verify`). What still passes: the `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_<n>` and `GIT_CONFIG_VALUE_<n>` environment variables, redirects into `.git/config` or `.git/hooks`, and obfuscated forms of the refused commands (1 to 6). `doctor` (`git.hooksPath`) notices a changed hooks path the next time it runs.

### Switching the hooks off

13. **The harness has to run them.** Claude Code holds hooks back until the workspace trust dialog is accepted (print mode and the SDK count as trusted). Codex needs a trusted project and a review of each hook in `/hooks`, and `--dangerously-bypass-hook-trust` runs hooks without review. Gemini CLI loads project hooks only in a trusted folder, and says nothing when it does not; a headless run needs `--skip-trust` or `GEMINI_CLI_TRUST_WORKSPACE=true`. Each harness also has a switch that turns hooks off (`disableAllHooks` in Claude Code settings, `[features] hooks = false` in the Codex config, `hooksConfig.enabled` in Gemini CLI settings), and project files that an agent can write can carry it. `doctor` (`hooks.switches`) reads these switches in the project files (it fails in `enforce` and warns in `observe`) and in the user's own files (it only warns). It cannot read any harness's trust state or managed policy, so a project whose hooks are not running can still look installed.
14. **Codex calls its hooks a guardrail.** Its documentation says tool hooks are "a useful guardrail, not a complete enforcement boundary", and that some specialised tool paths can opt out. Treat the Codex layer as weaker than the others.
15. **Gemini CLI marks nothing as a subagent call.** Its payloads carry no model, no prompt id and no subagent marker, so the hooks cannot tell a subagent's calls from the main agent's (the tool rules are applied to both), and built-in agents are refused in `enforce` because their model cannot be seen. If Gemini runs the prompt hook for a prompt that the main agent hands to a subagent, the hook cannot tell it from a human prompt. Whether Gemini does that is not verified. Hooks are not supported on Windows for Gemini in this version.
16. **A broken launcher is no launcher.** The Codex and Gemini CLI settings run `"$(git rev-parse --show-toplevel)/.sdlc/hooks/run.sh"`; Claude Code's first changes to `$CLAUDE_PROJECT_DIR`. Outside a git repository, in a clone or a worktree where the launcher is not committed (or is committed without the executable bit), the shell exits 127 with its own error, which the harness treats as non-blocking: nothing is checked. Commit `.sdlc/hooks/run.sh`; `doctor` (`hooks.<harness>`) warns when it is not committed or not mode 100755.

### Failing open

17. **Hooks fail open by design.** A hook must never stand between the agent and its work, so these let the action through, with one line `sdlc: hook skipped: <reason>` on stderr (Gemini gets `{}`): `sdlc` not found or exiting with an error, a payload the hook does not understand, a config that cannot be read or is not valid, a hook that runs past its timeout (15 seconds before a tool call, 30 for prompt and session start; the harness cuts it off, and the kit relies on it treating that as non-blocking), and any exception of the hook's own. Two more fail-open cases are quieter: when the task lookup fails (GitHub unreachable, `gh` not usable, or no answer within the 3 second deadline the lookup has before a tool call; 6 seconds for session start and prompt) the edit is allowed with the warning "could not read task #N; edit allowed", so a slow network weakens `enforce`, and when git fails in a file's directory so that its checkout cannot be resolved, the edit is allowed.

### Forging local state and approvals

18. **The local cache is writable by redirect.** `.sdlc/cache/` holds plain files that an agent with a shell can write: `hook-tasks.json` (the cached task state the edit rule reads; a forged entry says "the plan is approved" for up to ten minutes), `outbox.jsonl` (the queue of commands that wait for `sdlc sync`), `gaps.jsonl` (the gap log, which can also be edited to erase a record) and `sync.lock`. The cache is not in git, so a reviewer does not see it. Forging `hook-tasks.json` gives no power beyond shell-driven edits (8). **The control for the outbox is the replay allowlist**: `sdlc sync` replays only `stage start`, `stage publish`, `evidence add`, `review handoff`, `approve` and `task checkpoint`, refuses the options `--config`, `--verify`, `--json` and `--dry-run`, and never replays `task new` or `deploy record`, whatever a line says. A forged line can do no more than the agent could by running the same command. A malformed line moves to `outbox-failed.jsonl` and makes `sdlc sync` exit 1.
19. **An agent with a shell can call the prompt hook itself.** The `hook-spoof` rule refuses `sdlc hook` and the launcher in both modes, but it reads command text (1 to 6), so an agent that obfuscates the command can run `sdlc hook <harness> prompt` with a payload it wrote, and have `/approve` recorded. An agent that holds the owner's token can do more: post a comment as the owner, or write the state comment through `gh api`. The answer is the setup in "Recommendations": a separate agent account that cannot approve, and an owner who reads a task before merging it.
20. **Gemini has no prompt id, so a re-delivered `/approve` can count again.** For Claude Code and Codex, the reference of a prompt approval contains the harness's prompt id, so the same prompt delivered twice is one approval and cannot approve a later phase. Gemini payloads carry no prompt id, so the reference falls back to the action, or `approve-<phase>`. An old `/approve` that is delivered again after the task has moved to the next phase (by a replayed hook, per 19) is a different reference, and approves that phase.

### Limits that are not bypasses

21. **Replay can repeat a comment.** A queued command runs later against the current state. A command that half-succeeded before the connection dropped can post its comment twice when it is replayed. A `gh` write that is killed after 60 seconds may already have been applied by GitHub, so it is not queued: the command fails (exit non-zero) with "the request may or may not have reached GitHub, so check before re-running", and the person looks at the issue before running it again (a re-run of a write that is not idempotent can repeat it; `stage publish` skips a comment it finds already posted). Only a failure that shows GitHub was not reached (no network, a refused or reset connection, a gateway error, a rate limit, a network timeout reported by `gh` itself) is queued. The check that stops a retried `stage publish` from posting a second comment recognises its own earlier comment by the login `sdlc` acts as; when that login is unknown (an Actions `GITHUB_TOKEN` or an App token), the check is off and the comment is posted again. This costs noise, not authority.
22. **Gaps reach GitHub late and in part.** They are written locally and flushed by `sdlc sync` (at the next session start, or by hand), and only the 20 newest stay in the state comment. A gap belongs to a task: one logged where no task exists (a violation on a branch with no task) is dropped by the sync, with no call to GitHub.
23. **`--unverified` and a missing login.** In `observe` mode an approval from a login that cannot be told from the agent is recorded as `unverified`: a record, not a proof. A state comment written by a login the tool does not know (an Actions `GITHUB_TOKEN`) is not trusted as task state unless its author is an owner, an agent or `github-actions[bot]`.
24. **Time of check and time of use.** The hook decides on the state it read at that moment, or on a cache up to ten minutes old for an allowed edit. A task cancelled or reopened a minute ago may still let an edit through.

### Limits added with the hook fixes

25. **Kit removal is refused, not prevented.** `sdlc uninstall` and `sdlc init --overwrite-modified` are refused in both modes (`kit-removal`), in their wrapped forms too (`npx`, `pnpm exec`, `bash -c`) and run as `node dist/cli.js` or `node_modules/.bin/sdlc`, which the same rules read as `sdlc`. A copy of the CLI under another path or name is not read. `sdlc uninstall --dry-run` and `sdlc upgrade` are allowed. The shell can still delete the launcher, or rewrite the settings and the kit's files by redirect (8), and the obfuscated forms (1 to 6) are not read.
26. **MCP servers.** A server added through the protected config files (`.mcp.json`, the harness settings) is refused in `enforce`. A filesystem MCP server that is already configured writes files the edit rule does not see (9).
27. **A working directory outside the repository.** When the harness starts the hook in a directory that is not inside a checkout, the hook falls back to the harness's project directory (`CLAUDE_PROJECT_DIR` for Claude Code, `GEMINI_PROJECT_DIR` for Gemini CLI) and, for an edit, to the checkout of the edited file. Codex has no project directory variable, so it has only the edited file. When nothing resolves, an edit is let through with `sdlc: hook skipped`; a shell command is judged as in `observe`: `hook-spoof` and `kit-removal` are refused, the other rules warn, and no gap is recorded.
28. **The installed kit itself.** The hooks run whichever `sdlc` the launcher finds: the project's `node_modules` or a global install. An agent that edits those files (outside the repository, or under `node_modules`, which no review sees) changes what the hooks decide.
29. **The mode comes from the main checkout, for the harness hooks only.** A harness hook reads the worktree's `sdlc.config.yaml`, then takes `mode` (nothing else) from the main checkout's file when that file loads, whichever branch the main checkout is on and committed or not; `--config` wins over both. A main config that is missing or does not load is ignored without a message, and the worktree's own mode applies, so breaking that file switches nothing off that editing the worktree's own config did not already (8). The rest of the config, the git hooks and the `sdlc` commands still read their own checkout's copy and follow a mode change only once it is committed and reaches their branch; `sdlc config set` writes the checkout it runs in, so an owner who runs it in a worktree changes nothing for the hooks. Queued commands are replayed from the main checkout, with its config.
30. **The edit time of a PR body is read best effort.** The rule in "Approvals" (a comment is void once the PR body was edited after it) needs `lastEditedAt`, which only GraphQL gives. When that query fails (network, rate limit, a token without the right), the call carries on without the time and prints `warning: could not read when the body of PR ... was last edited`; an owner comment on a PR whose body was edited since is then counted as it was before the rule existed.

## Recommendations

1. **Give agents their own GitHub account**, listed under `agents`, with a token that has no admin rights and, where the plan allows, no right to merge into the default branch. This is the one measure that turns most of the bypasses above from "possible" into "possible, but the account cannot merge it". Keep the owner's token out of the agent's shell and environment.
2. **Protect the default branch for everyone.** Keep the classic protection `init` sets, and where the plan allows, add a ruleset that requires an approving review from someone who is not the agent's account and includes administrators. Without that, a merge is one command for any account with admin rights.
3. **Use `enforce` mode** once the team trusts the rules (`sdlc config set mode enforce`, then `sdlc upgrade`). In `observe` the hooks only warn and record gaps; the secret guard blocks in both.
4. **Keep the hooks running.** Commit `.sdlc/hooks/run.sh` with mode 100755; trust the project in each harness the team uses, and review the hooks in Codex's `/hooks`; run `sdlc doctor` and read `hooks.<harness>`, `hooks.switches` and `hooks.roundtrip`. Check once per harness, in `enforce`, that it refuses a command it must refuse: ask the agent to run `npx --no-install sdlc config set mode observe --dry-run` and see it refused (INSTALL.md, end of Step 6).
5. **Read what the agent changed**, not only what it says. Review the diff for changes to `.claude/settings.json`, `.claude/settings.local.json`, `.codex/hooks.json`, `.codex/config.toml`, `.mcp.json`, `.gemini/settings.json`, `sdlc.config.yaml`, anything under `.sdlc/`, and instruction files. Treat a pull request that changes them like one that changes CI.
6. **Keep secrets out of reach.** Use the OS keystore for the tokens, turn on secret scanning push protection, rotate any secret that was ever committed, and never paste a token into a chat. The local guard is a net, not a vault.
7. **Run `sdlc status` and `sdlc sync` now and then.** Look at the gaps on the tasks, at `Queued for sync`, and at orphan worktrees.
8. **Run agents in a sandbox when the stakes call for it.** A container or a virtual machine with no production credentials, and a token with narrow rights, protects what these hooks cannot.
