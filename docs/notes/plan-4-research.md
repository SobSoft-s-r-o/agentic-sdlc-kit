### A4. M11 package `files`: open (run on this tree)
- `npm pack --dry-run --json`: 498 files, 962,909 B tarball, 3.86 MB unpacked. By top dir: tests 223 files (1.76 MB), dist 156 (881 KB), src 78 (763 KB), docs 13 (342 KB), templates 21 (55 KB), INSTALL.md, README.md, LICENSE, package.json, tsconfig*.json, vitest.config.ts. No `.map` files; 78 `.d.ts` (tsconfig.json `declaration: true`); no `main`/`exports`/`types`, so the `.d.ts` serve nobody.
- Mechanism (verified in a scratch package, npm 10.9.4): `.gitignore` is honoured (a `.env` line excluded the file) but a directory holding a `bin` target (`dist/`) is packed whole although `dist/` is ignored. This repo's .gitignore (node_modules/, dist/, .sdlc/cache/, .worktrees/, .superpowers/) has no `.env`, so a stray `.env` in the working copy would be published. Without `files` the tarball depends on whatever sits in the directory.

Result: 181 files (156 dist + 21 templates + INSTALL.md + README + LICENSE + package.json), about 300 KB tarball (measured earlier in a scratch copy). Optional: `declaration: false` in tsconfig.json removes the 78 `.d.ts` (tests use tsconfig.test.json for typecheck; check it does not rely on emitted declarations).
- Runtime lookups, both relative to the module file, so layout `dist/<dir>/x.js` next to `templates/` and `package.json` must hold: `templatesDir()` src/render/templates.ts:9-11 (`new URL('../../templates/', import.meta.url)`), `packageVersion()` src/version.ts:11 (`../package.json`). Both are in the whitelist; docs/ and tests/ are not read at runtime.
- `prepare: tsc` (package.json "prepare"): runs on `npm pack`, `npm publish`, a bare `npm install` in the repo, and for git dependencies (`npx -y github:...#ref` today, so devDependencies typescript and @types/node are installed first, slow but works). It does NOT run when a registry tarball is installed, so registry consumers are unaffected if the tarball already contains `dist/`. `npm pack --ignore-scripts` still ran `prepare` here (npm 10.9.4). In a tree without node_modules `prepare` fails with `tsc: command not found`, so CI must `npm ci` before `npm publish`. Suggested: keep `prepare` (the github: install path in README/INSTALL/workflow still needs it), add `"prepack": "npm run build"` is redundant with it; better a guard test that `npm pack --dry-run --json` lists `dist/cli.js` and `templates/hooks/run.sh` and no `tests/`.

- Versions (https://docs.npmjs.com/trusted-publishers/): "npm CLI version 11.5.1 or later and Node version 22.14.0 or higher". - Provenance (same page): "provenance is generated automatically ... you don't need to add the `--provenance` flag", only for a public repository and a public package. A third-party report (https://philna.sh/blog/2026/01/28/trusted-publishing-npm/) says it had to pass `--provenance` anyway; to be safe set `"publishConfig": {"provenance": true}` (https://docs.npmjs.com/generating-provenance-statements/ lists `publishConfig`, `NPM_CONFIG_PROVENANCE` and `.npmrc` as equivalents; provenance needs npm >= 9.5.0 and `--access public` on the first publish of a scoped package). `npm publish --provenance` itself signs through Sigstore and logs to the public transparency ledger.
- `repository.url`: must match the GitHub repository exactly and case-sensitively ("`repository.url` ... must exactly match your GitHub repository"; provenance page: a public `repository` matching the source). This package.json has no `repository` field. Needed value: `{"type":"git","url":"git+https://github.com/SobSoft-s-r-o/agentic-sdlc-kit.git"}`.

Recommended afterwards: package setting "Require two-factor authentication and disallow tokens" (it affects only token auth), and revoke automation tokens.

The `npm trust` reference (https://docs.npmjs.com/cli/v11/commands/npm-trust/) says "The package you're configuring must already exist on the npm registry", needs npm >= 11.15.0, account-level 2FA, write access, and rejects bypass-2FA granular tokens; subcommands `github`, `gitlab`, `circleci`, `list`, `revoke`; flags `--file`, `--repo`, `--env`, `--yes`, and at least one of `--allow-publish` / `--allow-stage-publish`. Today `agentic-sdlc-kit` is a 404 on the registry, so the sequence is: owner runs a manual `npm publish` (2FA, with `files` and `repository` already in place, ideally as the version to ship), then `npm trust github agentic-sdlc-kit --file release.yml --repo SobSoft-s-r-o/agentic-sdlc-kit --allow-publish`, then every later release comes from the tag workflow.

## D. Dogfood (spec §15)

### How the launchers find sdlc
- templates/hooks/run.sh: `command -v sdlc`, else `command -v npx && npx --no-install sdlc --version </dev/null`, else prints "hook skipped: sdlc not found" and exits 0 (Gemini gets `{}`). templates/githooks/hook.sh: same order, else a stderr notice ("the secret guard is NOT active" for pre-commit and pre-push) and exit 0 into the legacy-hook chain. Neither ever downloads (`--no-install`).
- Measured here: with no global `sdlc` and no `node_modules/.bin/sdlc`, `npx --no-install sdlc --version` inside this repo (and its subdirectory `src/`) prints 0.2.0 and exits 0: npm exec resolves the current project's own `bin` (`dist/cli.js`). Outside the repo it fails with "npx canceled due to missing packages: sdlc@1.0.0". So the kit's own repo already resolves a repo-local built `dist/cli.js` with no setup, as long as `dist/` exists. Caveats: `dist/` is gitignored, so each new task worktree (`.worktrees/<n>-<slug>`) has no `dist/` or `node_modules/` until `npm ci && npm run build` runs there, and the hooks then skip silently (fail open); `dist/` goes stale after editing `src/` until rebuilt (the hook enforces the last build, not the code under edit); a build that fails to compile leaves the old output or none.

### Options for the kit's own repo (not decided)
1. Repo-local `npx --no-install sdlc` (as measured). Cost: zero change. Needs a build per worktree and after each source change; a broken build disables the guard; a stale dist enforces old rules. Fits: add `npm ci && npm run build` to the worktree setup step of the instructions.
2. `npm link` from the main checkout (global `sdlc` symlink; `command -v sdlc` wins in both launchers). One build, shared by all worktrees. Cost: machine-global (every other repo on the machine also runs the dev build, with kit_ref skew), per Node-version prefix with nvm, silently stale after a pull until `npm run build`, and a `link` is invisible in the repo (doctor's `sdlc.onPath` check passes for the wrong reason).
3. A config/launcher option: e.g. `kit.bin` (path to `dist/cli.js`, relative to the main checkout) rendered into run.sh and githook.sh, or an `SDLC_BIN` environment variable the launchers read before `command -v sdlc`. Gives worktrees a single shared build via `git rev-parse --git-common-dir`, and makes the choice explicit in committed files. Cost: new schema key plus render and doctor changes (src/config/schema.ts, src/render/hooks.ts, templates/hooks/run.sh, templates/githooks/hook.sh, doctor `secrets.guard`), a managed file that differs per repo, and an environment variable is one more way for a shell to redirect the guard (threat model entry on hook-spoof); a committed config key is owner-controlled and protected in enforce.
4. Dogfood the published package once it exists (`npm i -D agentic-sdlc-kit`, `npx --no-install sdlc`). Honest end-to-end test of the registry tarball; lags HEAD, and a broken release breaks the repo's own guard, so keep one of 1-3 as the escape hatch.
Combination worth weighing: option 1 for `main` plus option 4 in CI (install the tarball produced by `npm pack` and run `sdlc doctor --preflight`).
